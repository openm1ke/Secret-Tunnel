# Длительная работа Android и восстановление UDP — 24 ноября 2026

Ветка: `codex/android-long-session-stall`, база `34bacc4` (0.3.34).

Пользователь сообщил: через 30–60 минут работы по Wi-Fi контент перестаёт
загружаться или заметно замедляется; перезапуск туннеля помогает. Позднее
уточнил, что телефон находится далеко от точки доступа. Сам Realme для
снятия состояния недоступен. Поэтому ниже разделены воспроизведённые ошибки
кода и гипотезы о конкретном устройстве.

## Подтверждённые ошибки и исправления

**Завершение UDP-приёмника агента не завершало ассоциацию.** В `Relay` задачи
чтения могли закончиться с ошибкой, но их `JoinSet` никто не опрашивал.
Сокет оставался в `v4`/`v6`, поэтому новые отправки не создавали приёмник
заново. Исходящие повторы обновляли время активности: таймаут простоя тоже
не освобождал такую ассоциацию. SSH и другие соединения при этом могли
оставаться исправными.

Теперь `udp_association` наблюдает за завершением приёмников, сохраняет
причину и закрывает повреждённый поток. SOCKS-адаптер получает закрытие
управляющего соединения и может создать новую ассоциацию. Завершение уже
отменённого потока не считается новой ошибкой. Число событий хранится в
`udp_receive`; оно не прибавляется к числу потерянных датаграмм, которое
из ошибки приёмника определить нельзя.

Регрессия `a_failed_udp_reader_retires_its_flow_and_capacity_can_be_reused`
до исправления останавливалась по дедлайну: клиентский поток оставался
открытым после выхода приёмника. После исправления проходят оба случая
завершения задачи, освобождение единственного слота и настоящий UDP echo
через следующую ассоциацию. Проверено также в Ubuntu с Linux-бинарником.
Ошибка приёмника в тесте внедряется явно; это не доказательство возникновения
такой ошибки в сети пользователя.

**Ожидание записи в UDP-сокет могло удерживать окно после отмены потока.**
В клиенте и агенте `send_to().await` находился внутри обработчика пакета,
за пределами выбора события отмены. При остановившемся IO полученный пакет
и его кредит могли оставаться занятыми.

Общий `send_datagram` теперь прерывает такую отправку при закрытии потока
и ограничивает каждую попытку записи пятью секундами. Проверены остановившаяся
операция, дедлайн, отмена и возврат удерживаемого кредита в обеих ролях
мультиплексора. Обычно готовая запись выполняется сразу; таймер ограничивает
ожидание готовности сокета.

В Android добавлены счётчик ошибок приёма UDP, фиксация локальных ошибок
UDP и версия приложения/Android/модель в копируемом журнале.

## Длительный прогон исходной реализации

Путь: отдельное приложение `traffic-probe` → настоящий Android VPN/TUN →
hev-socks5-tunnel → общий Rust-клиент → SSH/OpenSSH → агент 0.3.34 в Ubuntu →
локальный TCP/UDP echo. Чужие серверы и публичные сервисы загрузок не
использовались. Адрес echo `203.0.113.10` назначен только внутри тестовой VM.

Длительный прогон выполнен на эмуляторе Android 17. На Android 14 отдельно
проверено восстановление при потерях; результаты сохранены в
[JSON замеров](benchmarks/android-long-session-2026-11-24.json).

| Показатель | Результат за 35 минут |
| --- | ---: |
| Полные TCP-загрузки по 128 КиБ с проверкой содержимого | 21 210 |
| Преднамеренные TCP RST для проверки уборки | 3 030 |
| Успешные UDP-обмены | 24 240 |
| Ошибки проверяемых загрузок / обменов | 0 / 0 |
| Отказы по лимиту клиента / агента | 0 / 0 |
| Ошибки протокола клиента | 0 |
| RSS Android-процесса | 203 504–206 080 КиБ |
| RSS агента | 1 708–2 552 КиБ |

Постепенного заполнения окон и роста числа открытых соединений в этом
сценарии не обнаружено. Растущие счётчики намеренных отмен/RST следует
отличать от ошибок успешно завершённых загрузок.

Отдельный прогон общего клиента через настоящий OpenSSH передал
1 207 959 552 байта в каждую сторону (1,125 ГиБ). Содержимое совпало;
переобмен ключами состоялся, ошибки TCP отсутствовали, очереди и удерживаемый
кредит после передачи вернулись к нулю. Длительность — 391,6 с. Дополнительно
тест с ускоренными переобменами ключей выполнил 800 TCP-соединений и
параллельный UDP без исчерпания повторно используемой ёмкости.

## Проверка восстановления и слабой связи

`benchmarks/ssh-transport/fault-udp-agent.py` в одноразовой SSH-фикстуре
отправляет Abort для одной UDP-ассоциации после 25 ответов. Остальные потоки
и SSH продолжают работу. Это проверяет реакцию Android-адаптера на результат
обработчика ошибки; сам обработчик приёмника отдельно проверяется Rust-тестом.

Далее `tc netem` воздействует только на TCP-порт тестового SSH: задержка
30±10 мс, потери 0,5%, затем короткий интервал 100% потерь и восстановление.
Из-за SSH-проброса до VM потери находятся на внутреннем TCP-участке пути,
а не на радиоинтерфейсе телефона. Это модель задержек и остановки доставки
байтов, не измерение настоящего Wi-Fi Realme.

В семиминутном прогоне Android 17:

- 3 766 полных TCP-загрузок, без ошибок;
- 4 300 UDP-ответов, четыре ожидаемых таймаута при внедрённых отказах;
- после восстановления связи счётчики ошибок перестали расти;
- новые TCP- и UDP-запросы продолжили выполняться;
- отказов по лимиту не было, PID агента оставался прежним;
- VPN оставался в состоянии «Работает», ручного перезапуска не потребовалось.

Поле `passed` самого генератора нагрузки требует нулевых потерь, поэтому
в отрицательном сценарии оно `false`. Отдельный критерий проверки
восстановления — успешные новые передачи и отсутствие новых ошибок на
контрольном интервале после снятия нарушений — выполнен.

Первый дополнительный прогон Android 14 прервался из-за SIGABRT процесса
эмулятора на Mac: стек содержит `grpc::internal::CallbackWithSuccessTag`.
Это не падение Android-приложения; такой прогон не считается успешным.
Повторная проверка на одном эмуляторе без параллельного экземпляра прошла:
за пять минут выполнены 2 800 TCP-загрузок без ошибок, получены 3 198
UDP-ответов. Два ожидаемых таймаута пришлись на внедрённые отказы;
после восстановления новые ошибки не появлялись. PID агента сохранился,
ручного перезапуска VPN не потребовалось. Наблюдаемый интервал полной
потери TCP-пакетов составил около 4,3 с; в прогоне Android 17 — около 6,5 с.

## Проверки кода и границы вывода

Прошли 58 тестов мультиплексора, 36 тестов общего ядра, 77 desktop-тестов
(5 специальных тестов пропущены), тесты агента и его интеграционные сценарии.
Типы и тесты мультиплексора проверены для Windows MSVC; выполнения Windows
в этом прогоне не было. Android-сборка для трёх ABI, JVM-тесты и lint прошли.

Воспроизведены и исправлены два пути, способные оставить UDP-поток без
полезного прогресса или удерживать его ресурсы. Причина конкретного сбоя
Instagram на Realme пока не установлена. Слабая связь может замедлять весь
SSH-поток из-за повторной передачи TCP; эхо-нагрузка не воспроизводит
внутреннее состояние QUIC/HTTP3 приложения, работу радио и ограничения Realme.

Для следующего сбоя пользователь согласился скопировать «Ещё → Журнал →
Копировать журнал» до перезапуска. Важны окна/очереди, отказы по лимиту,
heartbeat, повторы внешнего TCP, ошибки UDP и состояние второго SSH, если
он включён. Эти данные позволят связать исправленные пути с реальным событием.
