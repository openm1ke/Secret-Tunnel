# Выбор программ и проверка UDP — 7 ноября 2026

Пользователь подтвердил работу голоса и видеотрансляции Discord через туннель. Это пользовательская проверка, а не автоматический замер качества звонка.

## Выбор программ

Во вкладке «Приложения» теперь доступны поиск, список с галочками, фильтр «Только выбранные», обновление списка и добавление exe через диалог. Технические пути и компонент перехвата находятся в свёрнутых дополнительных настройках. Выбор сохраняется; при активном перехвате кнопка «Применить выбор» штатно перезапускает только движок перехвата, сохраняя SSH-туннель. Программе может потребоваться переподключение.

Сканер читает ярлыки меню «Пуск», записи установленных программ в HKCU/HKLM и приложения с открытыми окнами. Цели ярлыков и команды удаления не запускаются. Полного обхода дисков нет. На тестовой машине обнаружено 115 записей до финальной валидации и 114 доступных вариантов через нативный Rust API, включая Telegram, Firefox и Discord. Переносимые программы и некоторые Store-приложения могут потребовать ручного выбора exe.

Discord объединяется с точным путём Update.exe независимо от версии каталога app-*. Firefox включает основной exe, launcher приватного режима и updater из того же каталога. Telegram включает основной exe и найденный updater из его каталога. Общее правило для всех Update.exe не создаётся. Существующие ручные правила сохраняются.

Большие списки путей разбиваются на несколько правил, чтобы буфер движка не обрезал выбор. Некорректные правила проверяются при сохранении до остановки работающего перехвата. Добавлена видимая обратная связь: ранее состояние сообщения обновлялось, но сообщение не выводилось в JSX.

Проверки: реальное чтение установленных приложений Windows через нативный Rust API (`check_applications`); production frontend build; браузерный UI-тест с моками Tauri, использующий этот каталог (выбор Telegram/Firefox, сохранение групп с updater, поиск, фильтр выбранных, применение при активном перехвате). Макет проверен визуально в 1120×900 и 1120×780. Снимок: `docs/screenshots/applications-selector.png`. UI-моки не являются проверкой реальной загрузки драйвера; перехват TCP/UDP ранее проверен отдельно.

## UDP: методика

Через диагностический Windows embedded-клиент создавалась SOCKS UDP-ассоциация в одной SSH-сессии. На сервере временный Python echo слушал только loopback. Публичный UDP-порт и firewall не менялись. Проверялись точные байты, адрес отправителя, sequence и SHA256 тела; TCP/SSH обеспечивает транспортную целостность, собственного сжатия UDP у нас нет.

Каждый прогон: 20 echo-пакетов каждого размера 64, 1200, 8192 и 60000 байт; затем 2000 пакетов по 1200 байт, окно 64. Всего в трёх прогонах 6240 echo-датаграмм, все возвращены без повреждений и пропусков. Дополнительно после оптимизации прошли одновременные TCP HTTPS/UDP DNS и закрытие UDP вместе с control TCP.

| Показатель | До | После, прогон 1 | После, прогон 2 |
|---|---:|---:|---:|
| Полезная нагрузка в pipeline, Мбит/с | 9,872 | 11,417 | 11,528 |
| Получено / отправлено в pipeline | 2000/2000 | 2000/2000 | 2000/2000 |
| RTT p50 для 1200 байт, мс | 51,695 | 49,884 | 49,308 |
| RTT p95 для 1200 байт, мс | 74,335 | 68,935 | 56,579 |
| RTT p95 для 60000 байт, мс | 126,329 | 100,239 | 104,772 |

Это короткие последовательные замеры на одном маршруте, без искусственных потерь и без изоляции сетевой нагрузки. Наблюдался рост pipeline примерно на 16%; он не доказывает такой же выигрыш в других сетях или в Discord. RTT около 50 мс преимущественно связан с маршрутом. Реальные потери внешнего UDP тест не измеряет: данные до сервера передаются по надёжному TCP/SSH.

## Изменения транспорта

- Разбор числовых адресов без создания String и обратного преобразования в IP; проверка фреймов без лишних выделений памяти.
- Заголовок и тело передаются одним write в SSH-канал вместо отдельного сообщения с двухбайтовым заголовком.
- Серверный stdout обслуживает отдельный поток с BufWriter. Он объединяет только уже стоящие в очереди ответы (до 16), не ждёт накопления пакетов. Очередь ограничена 64 ответами.
- Для доменных адресов добавлен ограниченный кеш DNS: до 128 имён, 60 секунд. Числовые IP обходят DNS.
- До 256 UDP-потоков; неактивные 120 секунд освобождаются. Ошибка одного назначения не завершает все остальные потоки. Превышение лимита диагностируется, новые пакеты отбрасываются вместо падения ассоциации.
- Оборванный фрейм теперь является ошибкой, а не нормальным EOF.

На сервере агент обновлён атомарной заменой своего бинарника. Предыдущий сохранён в `~/.local/share/secret-tunnel/agent-before-optimization`; существующие процессы не перезапускались. Новый SHA256: `6b474b4899c4c92df491a09278534222bcbda8ef90d4dc4e5bd6fcd855b0c233`. Xray остаётся active. Системные настройки TCP, firewall и другие службы не менялись.

## Что улучшать дальше

Длительный тест с метриками очередей и задержек, нагрузкой голос+видео и контролируемыми потерями; затем распределение пропускной способности между потоками. Не включать сжатие Opus/видео без измерений: обычно это уже сжатые данные. Head-of-line blocking единственного TCP/SSH остаётся ограничением архитектуры и не устраняется оптимизацией агента.
