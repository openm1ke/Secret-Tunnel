# Аудит производительности и надёжности Secret Tunnel 0.3.6

База исследования — опубликованный `v0.3.6`, коммит `0743ef3`. Транспорт, SOCKS, планировщик и серверный агент уже написаны на Rust. Android использует тот же SSH-код, что и desktop, через JNI. Kotlin управляет Android VPN, профилями и интерфейсом. Нативный `hev-socks5-tunnel` преобразует пакеты TUN в SOCKS. Смена языка этих частей сама по себе не устраняет ни одну из подтверждённых задержек.

Наибольший выигрыш для голоса сейчас обещает контроль первых секунд TCP-загрузки. Самое конкретное исправление для надёжности — изолировать ожидание DNS внутри UDP-агента и отменять отложенную отправку при закрытии потока. Форк `russh` имеет смысл обсуждать после профилирования участка SSH с выключенным захватом и на одинаковой сети.

## macOS

Приложение уже собирается для macOS 13+ в universal DMG и ZIP с Apple Silicon и Intel. На Apple Silicon ранее проверены реальный TCP/UDP-перехват выбранного процесса, прямой выход другого процесса и очистка правил после завершения GUI. Релиз `0.3.6` прошёл сборку и проверку упаковки на macOS runner. Сейчас приложение имеет ad-hoc подпись, а внешний ProxyBridge устанавливается отдельно. Физический Mac в этой сессии не использовался. Intel пока подтверждён как архитектура сборки. Реальные звонки Discord, сон/пробуждение и смена сети на свежем DMG требуют отдельного прогона. [Релиз v0.3.6](https://github.com/openm1ke/Secret-Tunnel/releases/tag/v0.3.6) · [Нативная проверка](MACOS.md) · [Проверки упаковки](RELEASES.md).

Для перехвата приложений сейчас нужен установленный и разрешённый ProxyBridge Network Extension. Встроенный SSH с обновлённым агентом на конечном сервере обслуживает TCP и UDP. macOS-профиль ProxyBridge использует `dnsEnabled: false` и `sendDomain: false`, поэтому системное DNS может идти напрямую. Доменные regex-правила реализованы для Windows. При остановке desktop-перехвата выбранные приложения могут создать новые прямые соединения. Для режима «только через туннель» понадобится отдельная политика блокировки с проверкой отказов на каждой ОС. [Контракт текущего адаптера](../src-tauri/src/macos_redirect.rs) · [Проверенный ProxyBridge для macOS](https://github.com/InterceptSuite/ProxyBridge/releases/tag/v4.1.2_MacOS).

Сначала проверить и улучшить диагностику существующей интеграции. Для собственного расширения потребуется отдельно спроектировать системный жизненный цикл и распространение с подписью. Apple описывает варианты упаковки App Proxy Provider и требования для прямого распространения. [Apple TN3134](https://developer.apple.com/documentation/Technotes/tn3134-network-extension-provider-deployment?changes=_3__4).

## Где проходит пакет

```text
Android   VpnService → TUN → hev-socks5-tunnel ┐
Windows   WinDivert → ProxyBridge             ├→ локальный SOCKS5
macOS     Network Extension → ProxyBridge     ┘

SOCKS5 → Rust stream-mux → russh → SSH/TCP → серверный Rust-агент → TCP/UDP к цели
```

Промежуточный сервер в цепочке пробрасывает SSH к следующему. Агент работает на конечном сервере. Прямой маршрут полезен там, где он доступен. Цепочка решает задачу доступности, когда мобильная сеть не пропускает прямой SSH. Её эффект на задержку зависит от реального пути и замеряется отдельно. [Проверка мобильного маршрута](SSH-CHAIN-MOBILE-2026-11-10.md).

## Подтверждённые узкие места

**Очередь TCP перед включением приоритета.** Профиль 96 КиБ показал p95 UDP 204 и 484 мс, когда короткие UDP-пакеты шли до начала 16 TCP-загрузок. Контроль без ограничения дал 2,08 и 5,36 с. При одновременном старте в медленном сценарии только 331 из 600 ответов уложились в 700 мс. Ограничитель включается после серии коротких UDP и уже не может обойти поставленные в SSH/TCP байты. Замена шифра и изменение приёмной очереди russh не решают эту последовательность. TCP восстанавливает потерянные сегменты и отдаёт поток по порядку. Это ограничение сохранится у дополнительных каналов внутри того же TCP-соединения. [Замеры QoS](QOS-SCHEDULING-2026-11-10.md) · [Замеры шифров](SSH-CIPHERS-AND-LATENCY-2026-11-10.md) · [RFC 9293, §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2).

**DNS задерживает независимую работу внутри одной UDP-ассоциации.** В цикле агента каждая дейтаграмма с доменным адресом ждёт `lookup_host` перед чтением следующего кадра. Пока запрос ждёт, дейтаграммы к уже известным IP в той же ассоциации также ждут, а приёмный кредит остаётся занят. Если придёт `Abort` во время успешного отложенного lookup, агент может отправить уже принятую дейтаграмму после обработки отмены. Речь о SOCKS-пакетах с доменным адресом. DNS-пакет к заданному IP резолвера проходит другой путь. [Реализация UDP](../udp-agent/src/multiplex.rs).

Повторено на Linux-агенте из опубликованного `v0.3.6`, архив и бинарник сверены по SHA-256. Стенд через stdio запускал два настоящих UDP-потока `STMUX003` с QoS. Изолированный локальный DNS отвечал через 1,2 с. Контрольные пары без lookup пришли за 1,18 и 1,22 мс. Пять пар с lookup дали следующие результаты.

| Контрольный UDP к literal IP | Медиана | Диапазон |
|---|---:|---:|
| Та же ассоциация | 1203,16 мс | 1202,94–1363,59 мс |
| Другая ассоциация | 0,62 мс | 0,59–1,13 мс |

В отдельном случае отложенный положительный ответ DNS привёл к `udp_sent_after_abort: true`. После `Abort` агент успел принять новый поток, прежде чем отложенный пакет дошёл до UDP-эхо. Это воспроизведение локальной причины с контролируемым DNS. Частоту в Discord и Telegram предстоит оценить отдельно. [Данные](benchmarks/agent-dns-isolation-2026-11-10.json) · [Стенд](../benchmarks/ssh-transport/agent-dns-isolation.py) · [Запуск](../benchmarks/ssh-transport/README.md#agent-dns-isolation).

**Ресурсы сервера в уже измеренном сценарии.** В мобильном прогоне агент на FR показал пик RSS 2508 КиБ и пик CPU 4,01% одного ядра в двухсекундных выборках. Отдельный замер процесса SSH показал пик 2,5% одного ядра. Эти данные относятся к нашим нагрузкам и не дают предельной ёмкости для многих клиентов. В них видны ожидание UDP-кредитов и отбрасывания, а устойчивого насыщения CPU не видно. Переписывание агента или смена класса сервера по этим результатам не обоснованы. [Ресурсы агента](SSH-CHAIN-MOBILE-2026-11-10.md) · [Ресурсы SSH](SSH-CIPHERS-AND-LATENCY-2026-11-10.md).

## Порядок внедрения и критерии

1. **Исправить DNS и отмену в агенте.** Проверять закрытие потока до отправки после lookup. Отделить обработку IP от ограниченной очереди доменных запросов, объединять повторы одного имени, установить лимиты по байтам/слотам, срокам и числу выполняющихся запросов. Сохранять порядок к одной цели. Учитывать, что тайм-аут ожидания системного `getaddrinfo` может оставить работу в blocking-пуле. На текущем стенде цель — исправный IP-пакет в той же ассоциации отвечает сразу, а `udp_sent_after_abort` становится `false`. Дополнительно проверить тысячи повторов одного имени, отказ DNS, переполнение очереди и очистку после отмены. [Семантика blocking-задач Tokio](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html).
2. **Добавить измерение первых секунд и проверить стартовый бюджет.** Сравнить 96 КиБ как сейчас с небольшим начальным TCP-бюджетом, который растёт по `Delivered` при низкой задержке и без короткого UDP. Второй кандидат — ранняя активация при первом коротком UDP и уже растущей очереди. Начать с фиксированных пределов и гистерезиса. Цель на той же матрице — увеличить долю UDP в 700 мс в первые 3 с, без порчи TCP и с целевым падением TCP-скорости до 5% на контрольных TCP-only сценариях. Это критерии будущего сравнения, текущие измерения их не подтверждают.
3. **Расширить стенд и проверку восстановлений.** Текущий Python-мост задаёт задержку и скорость байтового потока. Для потерь, джиттера и переупорядочивания нужен отдельный Linux-стенд на изолированных интерфейсах, чтобы TCP проходил настоящую ретрансляцию. Пробное включение `netem` в частном сетевом namespace на WSL прошло. Нагрузки — TCP-only, голос, голос + 2/16 загрузок, DNS/QUIC и 2 параллельных клиента. Повторять одинаковую нагрузку не менее пяти раз на профиль с чередованием порядка. Сохранять p50/p95/p99, отдельно ответы в срок, опоздавшие и ненаблюдавшиеся до окончания опыта, TCP-байты и скорость, CPU-секунды на ГиБ, пиковую память/FD и время восстановления до первого успешного ответа. Затем повторить Discord вместе с Instagram и Telegram на телефоне и пройти живой macOS-чеклист.
4. **Профилировать по границам модулей.** Сопоставить `агент stdio → mux без SSH → mux по SSH → SOCKS через захват`. Использовать одинаковое содержимое, расписание и число потоков. Добавлять по одному слою. Снимать CPU и аллокации на клиенте, агенте и sshd отдельно. Для Android сравнить учёт/график включёнными и выключенными при одинаковом состоянии экрана. Если цена копирования в `russh` воспроизводимо велика, сравнить минимальный патч на том же коммите. Практический порог для усложнения поддержки — заметный повторяемый выигрыш, например от 15% CPU на одинаковом объёме, с теми же p95/p99 и тестами host key, rekey, отмены и TCP/UDP.

Выбор шифра Auto и выключенное сжатие остаются базой эксперимента. Прямой маршрут и цепочка измеряются раздельно. Один SSH/TCP остаётся транспортным ограничением задачи. При большом числе клиентов имеет смысл отдельно измерить ёмкость сервера по CPU, памяти, сокетам и очередям. Для ближайшего изменения достаточно исправления локального пути DNS и контролируемого A/B стартового бюджета.
