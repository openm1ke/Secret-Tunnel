## Приоритетные находки по исходникам

1. **P1: ложный running во встроенном SSH.** `embedded_ssh.rs:151–180`: start возвращает handle до SSH-аутентификации, ошибки runtime и run_embedded_tunnel теряются. `lib.rs:173` всегда возвращает Ok(None) для embedded. Остановка рабочего потока не отражается в статусе; reconnect не запускается. Ошибки отдельных SOCKS-соединений также отбрасываются (`embedded_ssh.rs:212`). Нужны подтверждение готовности и канал событий/ошибок, контроль завершения задачи.
2. **P1: окно может зависать.** Синхронные Tauri-команды выполняют sleep, DNS/TCP, curl/ssh output и ожидание процессов. tunnel_status удерживает runtime mutex во время измерений и IPinfo; curl может ждать 6 секунд, reconnect — до 120 секунд. Вынести жизненный цикл и измерения в фоновые задачи; IPC должен читать готовый снимок. Простого async поверх блокирующего I/O недостаточно.
3. **P1: счётчики Windows/Linux в OpenSSH отсутствуют.** `lib.rs:557`: sampler возвращает None. Нулевой график не означает отсутствие трафика. Показывать недоступность измерений либо считать байты в локальном forwarding-компоненте. Различать полезную нагрузку и байты транспорта с накладными расходами.
4. **P1: восстановление одноразовое и зависит от UI.** `lib.rs:1216`: обнаружение обрыва и reconnect запускаются запросом статуса. После неудачной попытки runtime уже None, следующая проверка не продолжает попытки. Нужен supervisor с отменой, backoff и состояниями connecting/running/reconnecting/failed/stopped.
5. **P1: возможная взаимная блокировка передачи embedded.** `embedded_ssh.rs:310`: после чтения из одного направления write_all ожидается внутри ветви select; обратное направление в это время не читается. Под встречной нагрузкой и backpressure возможна остановка прогресса. Нужны независимые копирующие задачи с корректным half-close и счётчиками; проверить одновременную передачу в обе стороны.
6. **P2: настройки embedded частично не действуют.** connect_timeout/compression/пользовательские keepalive не передаются; значения зашиты в connect_ssh. verify_proxy_on_start игнорируется. В lib.rs:1047 осталась ошибочная надпись о не реализованном direct-tcpip, хотя реализация есть. test_server всегда использует внешний ssh, даже при embedded.
7. **P2: история временная.** Логи — максимум 1000 строк в памяти, график — 120 точек; при запуске туннеля статистика очищается. Нет долговременного учёта, ротации файлов, уровней событий и экспорта диагностики. TCP connect latency до SSH-порта — не задержка внутри туннеля и не ping Discord.
8. **P2: хранение конфигурации.** Прямая запись fs::write без atomic replace допускает повреждение при аварии. IPinfo token хранится открытым текстом и передаётся curl в аргументах процесса. Маскирование UI не редактирует все сообщения SSH. Нужны атомарное сохранение, хранилище секретов ОС и редактирование диагностики.
9. **P2: защита слушателя.** Embedded SOCKS поддерживает no-auth, а bind address допускает внешний интерфейс. Для локального продукта ограничить loopback; сетевой доступ должен быть отдельной осознанной настройкой с защитой.
10. **P2: frontend опрашивает состояние каждые 2.5 секунды без защиты от перекрывающихся запросов** (`main.tsx:383,489`). При медленных командах очередь растёт и возможны устаревшие обновления. Предпочтительны события backend и один запрос состояния при открытии.

## Вывод о Rust и продукте

Backend уже Rust/Tauri, UI — React/TypeScript, стабильный транспорт — системный OpenSSH. Переписывание интерфейса на Rust не имеет доказанного выигрыша для скорости сети. Сохранить UI и исправить фоновые задачи, управление состоянием и измерения. Решение об оптимизации принимать после измерения CPU/RAM, throughput и задержек на одном сервере для обоих движков. Текущий проект следует считать прототипом до интеграционных испытаний.

SSH dynamic forwarding сейчас обслуживает TCP-соединения SOCKS-клиентов. Системный захват пакетов, автоматическая маршрутизация приложений, UDP и управление DNS не реализованы. SOCKS CONNECT не заменяет VPN.

## Выборочное туннелирование Discord, TCP и UDP

Реализуемо, но требует другой сетевой архитектуры:

`Правила приложений → системный захват/перенаправление → локальный сетевой движок → защищённый TCP+UDP транспорт → зарубежный сервер → интернет`.

Для Windows возможен WFP-based компонент с идентификацией приложения и перенаправлением TCP/UDP. Реализация callout-драйвера, его подпись и привилегированная служба существенно увеличивают стоимость; сначала стоит испытать готовый поддерживаемый движок. Другой путь — TUN с движком маршрутизации по процессам. Сам TUN или WireGuard не обеспечивает выбор процесса: нужна отдельная привязка соединений к приложению.

На сервере необходим соответствующий UDP-совместимый транспорт: например, IP-туннель WireGuard при доступном UDP. Это архитектурный кандидат, а не проверенная рекомендация для данной сети. Обычного sshd для UDP недостаточно. Не делать UDP-over-TCP основным голосовым транспортом из-за задержек при потерях.

В UI: выбор исполняемого файла, режим «через сервер/напрямую/блокировать», TCP+UDP, RX/TX и диагностика по приложению. Для Discord учитывать дочерние процессы и обновляемые пути. Явно определить поведение при обрыве: блокировать выбранное приложение либо разрешать прямой выход.

Учитывать DNS, IPv6, исключение собственного транспорта из перехвата, перезапуски процессов и возврат системных настроек после аварии. Логировать метаданные соединений и ошибки; зашифрованное содержимое Discord такой перехват не раскрывает.

Первый прототип: одно правило Discord, TCP+UDP через тестовый сервер, остальные приложения напрямую. Проверить вход, чат, голос, видео, DNS/IPv6, одновременную передачу, сон/пробуждение, смену Wi-Fi, обрыв сервера и повторное подключение. До этого нельзя обещать стабильность или повышение скорости.
