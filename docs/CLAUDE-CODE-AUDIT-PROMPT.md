# Задание для Claude Code · независимый аудит Secret Tunnel

Прочитай этот файл целиком и выполни задание в текущем checkout. Ты независимый разработчик, которому передали проект на проверку перед следующим циклом улучшений. Цель — оценить, где приложение теряет скорость или надёжность, проверить выводы команды и предложить порядок работ с измеримыми критериями. Сохрани результат на русском языке в `docs/CLAUDE-INDEPENDENT-AUDIT.md`.

## База и границы

- Начни с `git status --short --branch`, `git rev-parse HEAD` и `git rev-parse 'v0.3.6^{commit}'`. Запиши проверяемый коммит, ОС, архитектуру, доступные инструменты и устройство. Для релизного поведения используй `v0.3.6` (`0743ef3e45f1d73dcb377eee515471bf23ca7945`). Если текущий код отличается, укажи, к какой версии относится каждый вывод.
- Прочитай действующие инструкции репозитория. Сохрани чужие локальные изменения. Разрешены чтение, сборки, тесты и изолированные локальные эксперименты. В этой задаче создай отчёт и при необходимости отдельные файлы для воспроизведения. Изменения рабочего транспорта, профилей, серверов, драйверов и релизов оставь отдельной задачей. Коммиты и отправку в GitHub не выполняй.
- Для сети используй фикстуры с тестовыми ключами, loopback и изолированные интерфейсы. Не обращайся к пользовательским SSH-ключам, боевым хостам, токенам и ключам подписи. При нехватке платформы или оборудования зафиксируй, какие результаты недоступны и как их получить.
- Продуктовое ограничение — TCP и UDP идут внутри одного внешнего SSH/TCP-соединения на сеанс. Поддерживаются прямой SSH и цепочка через промежуточные серверы. Для надёжности также важны выбор приложений, сохранение профилей, понятный статус, учёт трафика и диагностика.

## Этап 1. Собственный разбор кода

До чтения существующих аудитов и их результатов составь карту потока данных и запиши первоначальные гипотезы. Используй исходники, конфигурацию сборки, тесты и документацию интерфейсов. Объясни, какая часть работает на каждом клиенте и на сервере, где пакет копируется или ждёт, как расходуются кредиты и кто освобождает ресурсы. Для каждого модуля назови уже предусмотренные меры защиты, оставшиеся риски и самый дешёвый способ их проверить.

| Область | Что проверить |
|---|---|
| Общий Rust-транспорт (`tunnel-core/`, `src-tauri/src/embedded_ssh.rs`, `src-tauri/src/ssh_transport.rs`) | SOCKS, проверка ключей хоста, запуск и отмена, вложенные SSH-звенья, очередь и окно `russh`, смена ключей внутри сеанса, отличие платформенных сборок. Различай задержку локальной записи и доставку на другой конец. |
| `stream-mux/` | Планировщик, ограничение TCP-байтов в пути, кредиты, справедливость между потоками, half-close, отмена, таймеры, контрольные кадры, ограничение памяти и поведение при одновременном старте UDP и загрузок. |
| `udp-agent/` | DNS и подключение к цели, изоляция потоков, срок жизни ассоциаций, поздние ответы, освобождение задач и сокетов. Разделяй ошибки DNS, отбрасывания ядра и ограничения туннеля. |
| Android (`android/`) | `VpnService`, разрешения и защита SSH-сокета от повторного перехвата, TUN и нативный адаптер, восстановление при смене сети, список пакетов, IPv4/IPv6, учёт трафика и цена фоновой телеметрии. |
| Windows и macOS (`src-tauri/`, `src/`, `routing-engine/`, `session-control/`) | Перехват выбранных приложений и helper-процессов, доменные правила там, где они реализованы, состояние при аварии или реконнекте, очистка правил, зависимости от драйвера и сетевого расширения. Различай поддержку архитектуры сборкой и проверку на устройстве. |
| Сборка, профили и диагностика (`scripts/`, `.github/workflows/`) | Воспроизводимость release-артефактов, миграция настроек, поведение с несовместимым агентом, проверка состояния и пригодность журналов для диагностики. |

Независимо проверь три варианта: точечные изменения в текущем коде, изменения в `russh` или Android-адаптере, более крупная переработка. Для каждого укажи измерение, которое оправдало бы работу, ожидаемую сложность, риск регрессий и способ отката. Если данных для выбора нет, предложи эксперимент вместо оценки прироста в процентах. Для внешних API и библиотек опирайся на первичные источники и версию из lockfile или закреплённый commit.

## Этап 2. Проверки и сверка с аудитом команды

1. Запусти уместные существующие проверки для доступной среды. Начни с целевых тестов `stream-mux`, `tunnel-core`, `udp-agent`, `routing-engine` и `session-control` с `--locked`, а также `python benchmarks/ssh-transport/test_bridge.py`. Сборку UI, Android, Windows или macOS и проверки реального перехвата добавляй по доступности. Запиши команды и результаты, включая причины пропуска.
2. Воспроизведи наиболее важные собственные находки. Для сетевых выводов сравнивай одинаковые объёмы и расписание нагрузки. Отделяй запуск от установившегося режима, p95/p99 полученных ответов от доли пришедших в срок, скорость TCP от CPU и памяти. Для причинной проверки добавляй по одному слою: агент по stdio, транспорт с SSH, полный путь через перехват. Указывай, какие условия менялись и сколько было повторов.
3. Только после фиксации первоначальных выводов прочитай [аудит команды](ARCHITECTURE-PERFORMANCE-2026-11-10.md), [замеры QoS](QOS-SCHEDULING-2026-11-10.md) и [инструкцию к стендам](../benchmarks/ssh-transport/README.md). Используй связанные данные для проверки. Для ключевых выводов команды поставь статус «подтверждено», «частично подтверждено», «опровергнуто» или «не проверено». Для каждого приведи основание и границы применимости. Отдельно укажи собственные находки и расхождения с приоритетами команды.

## Формат результата

1. **Краткий вердикт.** Что уже работает, что следует исправить первым и оправдана ли смена реализации агента или SSH-библиотеки.
2. **Среда и проверяемые версии.** Коммиты, платформы, устройства, команды и фактически полученные результаты.
3. **Находки по приоритету.** Для каждой дай `P0–P3`, статус доказательства, путь и строку, условия проявления, эффект для пользователя, шаги воспроизведения, минимальное исправление и критерий проверки. Различай «воспроизведено», «видно из кода» и «гипотеза».
4. **Сверка с предыдущим аудитом.** Таблица «утверждение → независимый результат → доказательство или недостающая проверка».
5. **План по модулям.** Назови до трёх первых работ в рекомендуемом порядке. Для каждой укажи контрольный вариант, метрику успеха, допустимый компромисс и условия, при которых стоит остановить эксперимент. Остальные предложения оставь отдельным списком.

В итоговом сообщении дай ссылку на отчёт, три главных вывода и перечень проверок, которые требуют живого устройства или отдельной среды.
