# План развития Secret Tunnel — 9 ноября 2026

Основание: [аудит da9ab22](AUDIT-2026-11-09.md). Цель — простой per-app SSH-туннель для стабильного TCP/UDP, с понятным подключением, управлением маршрутами, счётчиками и объяснимыми ошибками. Этапы ниже последовательны по зависимостям, не являются обещанием календарных сроков.

**Ход выполнения:** в рабочей ветке реализованы исправления отмены, desktop supervisor, Android recovery и атомарное хранение/фоновая телеметрия. Результаты и оставшиеся проверки — [STABILIZATION-2026-11-09.md](STABILIZATION-2026-11-09.md). До завершения первого этапа остаются мастер установки агента, аппаратные аварийные проверки и длительный soak; весь этап пока не объявляется завершённым.

В 0.3.0 добавлены preflight и проверяемый серверный установщик. Клиент и агент используют STMUX003. Обновление APK поверх 0.2.3 и per-app VPN проверены на realme RMX3630. Следующий замер воспроизводит рост p95 UDP под TCP-нагрузкой на контролируемых echo-целях. Затем можно сравнить варианты планировщика потоков и лимитов очередей. ## 1. Стабилизация перед следующим patch-релизом

**Приоритет: P1, начать с этого.**

1. Исправить отмену STMUX (A1/A2): терминальное состояние должно быть доступно поздним подписчикам, все операции relay должны завершаться при Abort/остановке транспорта. Отдельно сохранить корректный TCP half-close.
2. Перенести desktop reconnect из `tunnel_status` в supervisor. Управляющие команды меняют desired state; generation/session ID запрещает завершившейся старой операции запускать новый туннель после Stop.
3. Добавить восстановление Android engine, не только SSH. Падение/рестарт tun2socks, смена capabilities IPv6, revoked VPN permission — отдельные переходы автомата.
4. Сделать конфигурацию desktop атомарной и сериализованной. Ошибку восстановления профиля показывать, не уничтожая последнюю валидную копию.
5. Добавить диагностическое обнаружение старого/отсутствующего v3 агента до включения interception/VPN.

**Проверяемая готовность:**

- Оба [новых теста](audit-repros/mux-cancellation/README.md) проходят; к ним добавлены настоящие socket-тесты в обоих направлениях.
- 1000 циклов connect/cancel/stop при медленных получателях: task/socket/queue counters возвращаются к базовому состоянию, FD не растут от цикла к циклу, память после прогрева выходит на плато. Проверять RSS/PSS отдельно от счётчиков mux.
- Stop во время DNS/SSH handshake/backoff не приводит к последующему скрытому подключению. Для in-memory supervision-тестов отмена укладывается в 1 секунду; сетевые дедлайны отдельно заданы и ограничены.
- Несколько неудачных reconnect не прекращают попытки до Stop/terminal auth error; ошибки ключа и изменённого host key не повторяются бесконечно без участия пользователя.
- Подмена config на неполный JSON и авария записи восстанавливаются из последней валидной версии.
- При падении engine UI не говорит «Работает», пока целевой путь TCP/UDP не восстановлен.

## 2. Гарантии маршрутизации и восстановление сети

**Решить до обещаний «весь выбранный трафик всегда через туннель».**

- Ввести политику отказа профиля: `блокировать до восстановления` / `разрешать напрямую`. Строгий режим реализовать системно, независимо от окна UI и живого SSH-процесса. Его точные границы зависят от ОС.
- Android: согласовать always-on/lockdown с платформой, обработку process death, foreground service, revoke, Doze, Wi-Fi↔LTE, потерю DNS и смену default network. При новой IPv6 capability перестраивать TUN контролируемо либо сохранять явно ограниченный IPv4 режим.
- Windows: отдельная политика WFP-блокировки выбранных приложений; не считать наличие WinDivert само по себе kill switch.
- macOS: определить поддерживаемый контракт DNS с Network Extension. Системный DNS и правила приложений проверять отдельно. Общие Electron-утилиты привязывать к path/signing requirement, если это поддерживает выбранный компонент; иначе честно показывать расширенный охват правила.
- Для каждого режима проверить новые и уже установленные TCP/UDP, IPv4/IPv6, DNS, DoH/DoT, QUIC, сон/пробуждение и аварийное закрытие GUI/SSH/agent.

**Готовность:** в строгом режиме пакетный захват на контролируемом стенде не показывает DIRECT выбранного тестового приложения при указанных отказах; исключённое приложение остаётся напрямую. Intentional DIRECT доменных правил — отдельное, явно проверяемое исключение. Ручной Stop выполняет выбранную пользователем политику, а не случайное поведение движка.

## 3. Простое подключение и надёжные профили

- Мастер: «сервер» → «проверка подлинности» → «проверка доступа» → «агент» → «приложения» → «подключение». Не объединять ошибки этих этапов в общее «SSH не работает».
- Добавить agent `--version/--capabilities` со стабильным машинным JSON: protocol versions, TCP/UDP, архитектура, сборка. Отображать совместимость до установки маршрутов.
- Установка/обновление агента через уже авторизованный SSH в `~/.local/bin`: SHA256, architecture check, self-test, atomic replacement, backup и rollback. Не менять sshd, Xray/wstunnel, чужие ключи и system services. Существующие сессии и новые версии проверить отдельно.
- Credential repository: Android Keystore, Windows Credential Manager/DPAPI, macOS Keychain. Секреты исключить из JSON/argv/экспорта. Импорт ключа проверять парсером до замены рабочего ключа.
- Вынести Android импорт/enrollment из Activity в lifecycle-safe операции с generation/profile ID. Различать «добавлен на сервере», «проверен новый вход» и «сохранён локально»; при прерывании давать безопасный путь продолжения/отзыва.
- Общий набор параметров SSH: timeout/keepalive/engine capabilities. Скрывать неработающие настройки или помечать область применения; кнопка «Проверить» должна использовать выбранный движок.
- Экспорт/импорт профилей без секретов и с версией схемы. Изменения активного профиля — только через явное переподключение.

**Готовность:** установка на чистый поддерживаемый сервер и обновление со старого агента проходят по одному понятному сценарию; неуспешная установка оставляет рабочую предыдущую версию; rotation/kill UI не повреждают рабочий ключ.

## 4. Качество голоса/видео и диагностика

Наращивать число потоков без измерения задержек не следует. Наличие 2048 TCP и 1024 UDP в синтетическом отчёте не доказывает качество разговора при загрузке канала.

- Зафиксировать baseline для текущего v3: throughput, p50/p95/p99 latency, jitter, полезные drops, reconnect time, CPU, RSS/PSS, battery и FD. Обязательные условия — без нагрузки, bulk download/upload, один не читающий получатель, слабая сеть.
- Ввести справедливый scheduler по потокам. Для UDP/интерактивного класса — небольшие очереди, ограничение возраста пакета и счётчик expired; для bulk TCP — throughput без starvation других потоков. Классификацию делать явно, без обещания распознать «голос» по каждому произвольному порту.
- Не увеличивать сразу все окна и буферы. Проверить профили `low-memory`, `balanced`, `throughput`; лимиты учитывать и по общей, и по доступной памяти. Нужны benchmarks разных RTT; 64 KiB credit window может ограничивать отдельный поток на длинном RTT.
- Добавить bounded DNS cache в v3 с корректными TTL/negative caching и Happy Eyeballs; не держать DNS cache бесконечно и не превращать устаревшие записи в обход domain rules.
- Ограничения единственного SSH/TCP сохраняются: TCP loss вызывает общий head-of-line blocking. Сначала измерить улучшения scheduler/буферов, а не обещать устранение этого свойства. Альтернативные транспорты рассматривать только если пользователь изменит требование «одно SSH-соединение».
- Диагностика: коды ошибок и этап, session/flow ID, negotiated agent version, очередь/лимит, rejected, drops по причине и месту, возраст server telemetry. Бounded logs с ротацией и экспортом после удаления адресов/секретов.
- Развести метрики: RTT до SSH, RTT внутри туннеля, байты полезного приложения и SSH overhead. Не выдавать общий mux-counter за статистику конкретного приложения.

**Критерии качества:** прогон на одном и том же стенде с baseline до/после, без потери TCP/half-close; p95/p99 коротких flow и UDP под bulk-нагрузкой не ухудшаются. Численные SLO голоса выбрать после измерений на настоящем телефоне и нужном сервере, не переносить результаты localhost на мобильную сеть.

## 5. Расширение функций после стабилизации

- Общий UI статуса: отдельно «SSH», «агент», «перехват», «доступ в интернет»; один основной следующий шаг, время переподключения и причина. Нельзя красить весь статус зелёным только потому, что процесс жив.
- Профили маршрутизации: наборы приложений, группы/поиск, импорт существующих правил, объяснение «какое правило сработало». Семантика direct/tunnel/block и порядок правил едины; платформенно неподдерживаемые действия явно недоступны.
- Доменные режимы: начать с exact/suffix/wildcard для большинства пользователей, regex оставить в расширенном режиме. Реализацию Android/macOS делать через надёжный DNS/flow mapping и политику для ECH/DoH/QUIC, а не слепое преобразование домена в постоянный IP. Обновление DNS не должно ломать исключения/CDN.
- Статистика по приложению: расширить контракт Windows/macOS interception и Android UID/flow attribution. Обычный входной SOCKS не знает исходный процесс, поэтому одних общих Rust-счётчиков недостаточно. Добавить причины отказа/дропов и правила хранения истории без списка посещённых сайтов по умолчанию.
- Проверка доступности профилей, ручной failover на другой сервер; автоматический failover — только после проверки host trust, исключений и fail-closed политики. У одного приложения не должно быть скрытой смены выбранного сервера.
- Экран «проверить соединение»: DNS, TCP, UDP, IPv6, агент, тест скорости по запросу. Диагностический probe ограничить по трафику и времени, не запускать измерения на каждом status poll.
- Accessibility: TalkBack/keyboard, font scale 1.0–2.0, landscape, маленькие экраны, экран ошибок без обрезанных кнопок. Вынести строки в ресурсы и состояния из presentation-кода.

## Техническая структура и процесс

1. Общий workspace/явные crate: transport protocol, SSH session, routing policy, telemetry. Убрать обратные `#[path]` зависимости `tunnel-core` на desktop `src-tauri/src` после регрессий; не создавать параллельную копию протокола.
2. Desktop Tauri commands — тонкий слой над supervisor/config repository. Android JNI — thin adapter; Kotlin отвечает за VpnService/lifecycle/UI, Rust — за transport. Избегать монолитного общего mutex на сеть и UI.
3. В CI на каждый PR: fmt/clippy, unit, protocol/parser/property/fuzz smoke, mock UI, desktop compile на Windows/macOS, Android unit/lint/build. Nightly/release: локальный SSH fixture + agent + реальный VPN на эмуляторе; нагрузка, fault injection и soak. Не использовать пользовательские ключи/сервер в обязательном CI.
4. Regression A1/A2 уже добавлены в основной `stream-mux` suite; туда включены повторные отмены и настоящие TCP-сокеты. Диагностический crate сохранён как история воспроизведения, а отдельные проверки session-control включены в Windows/macOS CI и release gate.
5. Публиковать неизменяемые версии: не заменять assets через clobber для уже стабильного тега; подписанные manifest/checksum, SBOM/provenance, фиксированные версии инструментов и SHA Actions, RustSec/cargo-deny. Apple Developer ID + notarization и Windows Authenticode — отдельные организационные задачи, требующие соответствующих сертификатов.
6. Прогон установленных release APK/EXE/APP важнее одной компиляции: обновление поверх предыдущего релиза, сохранение профилей/ключей, чистая установка, rollback. macOS Intel и Apple Silicon проверять как две runtime-платформы, не только две архитектуры файла.
7. Оформить PR этой ветки в main после A1–A4. Текущий успешный v0.2.3 CI — хорошая исходная точка, но новые находки должны быть закрыты regression-тестами до следующего обещания повышенной надёжности.

## Что сознательно не делать сейчас

Не переписывать Kotlin/React целиком на Rust, не менять рабочий серверный стек, не добавлять несколько транспортных соединений против текущего требования, не расширять без измерений лимиты до тысяч потоков на слабых устройствах и не начинать с большого списка новых функций до исправления cancellation/reconnect.
