# Диагностика SSH и восстановление мобильной сети

## Что изменено

Продолжение [исследования шифров и задержек](SSH-CIPHERS-AND-LATENCY-2026-11-10.md). Изменения относятся к следующей сборке после опубликованного v0.3.5.

Общий движок Windows/Android теперь наблюдает **физический TCP-сокет до первого SSH-сервера**. На Linux/Android доступны RTT, RTO, повторно переданные сегменты и байты, неотправленные байты, очередь сокета и окно перегрузки. На Windows используется `SIO_TCP_INFO`: набор полей меньше, отсутствующие значения остаются `null`. Для цепочки RU → FR эти значения описывают клиент → RU; серверный `ss` отдельно описывает RU → FR. Они не являются RTT всего маршрута.

Обёртка сокета не дублирует дескриптор и не продлевает жизнь соединения. Чтение метрик и закрытие синхронизированы, поэтому диагностика не может обратиться к уже переиспользованному дескриптору. Старые Android-ядра могут возвращать короткую структуру `TCP_INFO`; поля проверяются по фактической длине.

Android показывает метрики в «Журнале» и пишет изменившиеся снимки в `SecretTunnelTcp` не чаще раза в пять секунд. Windows добавляет `SSH TCP` в журнал и возвращает снимок в статусе клиента. При ошибке системного API туннель продолжает работу, источник и код ошибки доступны в снимке.

В диагностику мультиплексора добавлены:

- PID процесса, включая отчёт серверного агента: можно сопоставить конкретного клиента с его агентом и SSH-соединением;
- число эпизодов исчерпания окна UDP;
- время от первого отказа по окну до следующего корректного Credit этого потока;
- последний такой интервал с временем, ID потока и количеством возвращённых байтов/слотов.

Один эпизод может содержать несколько отброшенных датаграмм. Следующий Credit не обязательно полностью восстанавливает окно и не обязательно относится к последнему пакету. Метрика не подменяет индивидуальный RTT пакетов. Незавершённый эпизод учитывается в числе событий, но ещё не имеет измеренной длительности.

## Настройки SSH

В Android: «Прокси» → «Изменить» → «Расширенные · SSH». В Windows: «Настройки» → «Расширенные · Embedded SSH».

Доступны:

- автоматический выбор, AES-128-GCM или ChaCha20-Poly1305;
- стандартная очередь 32 сообщения / приёмное окно 2 МиБ;
- экспериментальный профиль 8 сообщений / 1 МиБ.

Настройки применяются ко всем звеньям цепочки при следующем подключении. В Android они сохраняются в профиле прокси, текущий сеанс использует неизменяемый снимок. В Windows относятся к встроенному SSH-движку; системный OpenSSH их не использует. Ручной выбор задаёт единственный разрешённый шифр, поэтому несовместимый сервер даст ошибку согласования, а не незаметное переключение.

**По умолчанию сохранены Auto, 32 сообщения / 2 МиБ, сжатие выключено.** Окна UDP не изменены: загрузка 256 КиБ / 192 слота, стандартная отправка 128 КиБ / 128 слотов. Очередь в сообщениях и окно приёма SSH — разные ограничения; эти два готовых профиля меняют их одновременно и не позволяют отдельно оценить влияние каждого параметра.

## Найденная проблема мобильного соединения

Во время работы старого сеанса физическая сеть сменилась с 398 на 401. Старый сокет показывал RTT около 1,7 с, RTO 18,512 с, 53 повторно переданных сегмента, 43 816 повторно переданных байт и 7 320 байт в очереди. Новый пинг до RU при этом занимал около 48–50 мс. Это указывало на застрявшее старое TCP-соединение; менять шифр для такого случая недостаточно.

Добавлен `UnderlyingNetworkTracker` и callback основной сети. При её смене клиент переподключает SSH, сохраняя VPN-интерфейс. Пока сети нет или она устанавливается, интерфейс показывает ожидание/смену сети; ожидание не расходует попытки восстановления. Новая сеть сбрасывает backoff один раз, а повторные ошибки на той же сети по-прежнему ограничены существующей политикой восстановления. Поздний `onLost` старой сети и повторные capabilities новой сети не сбивают состояние. Изменение сети во время handshake обнаруживается после его завершения.

### Проверка на realme RMX3630

На обновлённом телефоне кратко отключены и снова включены мобильные данные. Wi-Fi не предоставлял альтернативного соединения. После теста мобильные данные включены.

- До отключения: физическая сеть 406, VPN 407, `tun0`.
- Без сети: VPN 407 и `tun0` сохранились.
- После возврата: физическая сеть 408, тот же VPN 407 и `tun0`, новый PID серверного агента.
- Новый сеанс обнаружен через **7,92 с** после команды включения мобильных данных. Это наблюдаемое время с дискретным опросом, включая восстановление сети и появление диагностики, а не чистая длительность SSH-handshake.
- Через восстановленный сеанс получены 4 МиБ TCP, **540/540 UDP** по 900 байт и **48/48** коротких эхо-ответов.

Проверки данных открывали локальный SOCKS телефона. Они подтверждают восстановление транспорта и сохранение VPN-интерфейса; поведение длительного голосового звонка при переключении сети этим тестом не проверено. Уже открытые TCP-потоки приложений не мигрируют в новый SSH-сеанс, приложениям потребуется открыть их заново.

## Сравнение профилей под нагрузкой

Маршрут: клиент → RU SSH → FR SSH → пользовательский агент. Ключи серверов проверялись. Нагрузка: две TCP-загрузки по 4 МиБ, три UDP-всплеска по 180 пакетов по 900 байт и 48 эхо-пакетов по 160 байт с дедлайном ответа 700 мс. TCP-производитель выдаёт 16 КиБ примерно каждые 10 мс на поток; это ограниченная нагрузка, не измерение предельной пропускной способности линии.

p95 вычисляется по полученным вовремя эхо-ответам. Число ответов показано отдельно: пропуск дедлайна не тождественен безвозвратной потере в сети. UDP-всплески специально создают давление на ограниченное окно; эти потери нельзя переносить на обычный голосовой трафик.

### Android, одна серия

Одна подписанная APK, встроенный движок ring. Для каждого профиля подтверждены неизменность физической сети и PID агентского сеанса во время измерения. Порядок: Auto/8 → AES/8 → AES/32 → Auto/32.

| Профиль | TCP, Мбит/с | UDP из 540 | Эхо из 48 | p95 эхо, мс |
|---|---:|---:|---:|---:|
| Auto / 32 / 2 МиБ | 4,89 | 538 | 48 | 545 |
| AES-128 / 32 / 2 МиБ | 3,17 | 231 | 41 | 571 |
| AES-128 / 8 / 1 МиБ | 4,60 | 372 | 46 | 456 |
| Auto / 8 / 1 МиБ | 4,68 | 362 | 45 | 355 |

На сервере отбрасывания UDP в этой серии совпали с нехваткой слотов: 2 / 309 / 168 / 178 соответственно. Максимальное время от первого отказа до следующего Credit — 12 / 52 / 136 / 346 мс. Максимальное удержание принятого UDP сервером — 0 мс в разрешении таймера, очередь Credit — до 4 мс. Это различает нехватку окна и медленную обработку на сервере, но не объясняет индивидуальную задержку каждого Credit по всем звеньям.

Предыдущий отдельный Auto/32-прогон на том же телефоне дал 7,78 Мбит/с, 540/540 UDP и p95 167 мс. Изменчивость мобильного пути велика. Одной серии и одинакового ID сети недостаточно, чтобы приписать разницу только шифру/очереди. Фоновая активность девяти выбранных приложений также не запрещалась. Мобильные пробы идут через локальный SOCKS, минуя перехват выбранного UID в TUN.

### Windows, три повтора

Для сравнения использован отдельный пример общего движка `check_route`, backend ring. Это **не** криптографический backend готового Windows GUI (aws-lc). Во время части серии локально шла Android-сборка. Числа нужны для обнаружения выбросов и дальнейшего планирования, а не для объявления оптимального профиля.

| Профиль | TCP в повторах, Мбит/с | p95 эхо, мс | Эхо из 48 |
|---|---|---|---|
| Auto / 32 / 2 МиБ | 13,76 / 12,62 / 13,32 | 125 / 125 / 109 | 48 / 48 / 48 |
| AES-128 / 32 / 2 МиБ | 3,83 / 12,02 / 1,22 | 406 / 125 / 687 | 48 / 48 / 11 |
| AES-128 / 8 / 1 МиБ | 13,17 / 12,09 / 14,96 | 79 / 110 / 78 | 48 / 48 / 48 |
| Auto / 8 / 1 МиБ | 14,82 / 1,54 / 15,44 | 79 / 594 / 78 | 48 / 27 / 48 |

В большинстве повторов принято 540/540 UDP; в третьем AES/32 — 528/540. Внешний Windows TCP-снимок не показывал retransmit timeout или повторно отправленные байты даже при выбросах. Поэтому только по этому снимку нельзя локализовать проблему во вложенном SSH/серверном участке. Настройка меньшей очереди остаётся экспериментом.

Отдельно проверен **собранный Windows GUI** с aws-lc, встроенным frontend, изолированным профилем и SOCKS 1083: HTTPS, 8 UDP DNS-ответов, закрытие UDP-ассоциации вместе с управляющим TCP. Этот smoke test прошёл; существующие пользовательские настройки Windows не менялись.

Машиночитаемая сводка: [ssh-transport-2026-11-10.json](benchmarks/ssh-transport-2026-11-10.json). Сырые журналы, снимки и локальные конфигурации остаются в игнорируемом `artifacts/latency-study`.

## Дальнейшие изменения

1. Повторить Instagram + Telegram + Discord на стандартном профиле и сопоставить конкретные задержки с двумя TCP-участками, эпизодами нехватки окна и очередью отправки. Проверить сохранение звонка после смены сети отдельно.
2. Добавить подтверждаемый heartbeat мультиплексора: он даст задержку полного маршрута даже без полезного трафика. RTT первого TCP не заменяет такое измерение.
3. Сравнить ограничение заранее поставленных bulk-данных, меняя по одному параметру за раз. Уменьшать очередь только после повторяемого выигрыша своевременной доставки UDP при приемлемой TCP-скорости.
4. Отдельно проверить объединение готовых Credit одного потока без таймера ожидания и завершение осиротевших агентских сеансов после исчезновения клиента.
5. До воспроизводимых результатов сохранить Auto/32/2 МиБ и выключенное сжатие. Микротест AES показывает стоимость вычислений, но пока не доказывает ускорение приложений по этому мобильному маршруту.
