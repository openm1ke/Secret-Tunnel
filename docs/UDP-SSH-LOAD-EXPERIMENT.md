# Голосовой UDP в отдельном SSH под нагрузкой

Эксперимент в ветке `codex/udp-ssh-load` на базе `54af68c`. В Linux VM запускаются актуальные встроенный Rust-клиент, OpenSSH и серверный агент 0.3.24. Для разделённого режима запускаются два экземпляра того же клиента с разными локальными SOCKS-портами. Нагрузочный стенд направляет короткий UDP в один порт и остальной трафик в другой. [Стенд и команда запуска](../benchmarks/ssh-transport/README.md#one-versus-two-ssh-connections-on-linux)

У каждого SSH своя внешняя TCP-сессия. Оба проходят через общее ограничение `netem` на первом участке. Второй SSH-узел цепочки доступен через loopback сервера. На первом участке задано 5 Мбит/с в каждом направлении, 50 мс задержки в одну сторону, джиттер 10 мс, 0,3% случайных потерь и очередь до 96 пакетов. Настройки SSH одинаковы. Клиент использует окно 4 МиБ, очередь канала 32 сообщения и TCP-бюджет 96 КиБ при распознанном голосе. Порядок одного и двух сеансов меняется между повторами.

Модель голоса отправляет 160 байт каждые 20 мс. Считаются время до ответа, доля ответов до 200 мс, отсутствие ответа и максимальная серия поздних или отсутствующих ответов. p95 считается среди полученных ответов. При TCP учитывается только период передачи четырёх файлов с проверкой SHA-256. Крупный UDP отправляет датаграммы по 1200 байт. Это модель нагрузки на транспорт, а 200 мс RTT служат порогом сравнения на стенде. Для реального звонка нужны метрики входящего и исходящего голоса, пауз и переподключения.

## Результаты

Ниже диапазоны двух повторов. Крупный UDP предлагал 5,76 Мбит/с полезной нагрузки на направлении отправки, при полном эхе столько же на обратном. Оба SSH делили лимит 5 Мбит/с в каждом направлении.

| Нагрузка | p95 короткого UDP, один → два SSH | Ответы до 200 мс, один → два SSH | Полезная скорость TCP, один → два SSH |
| --- | --- | --- | --- |
| Только короткий UDP | 204–209 → 201–204 мс | 92% → 92–95% | — |
| Скачивание TCP | 348–375 → 216–373 мс | 29–30% → 43–86% | 3,09–3,24 → 3,07–4,21 Мбит/с |
| Отправка TCP | 366 → 319–349 мс | 23–31% → 30–66% | 3,02–3,04 → 3,49–3,91 Мбит/с |
| Крупный UDP на другом сеансе | 937–1233 → 229–396 мс | 0,2% → 26–76% | — |
| Крупный UDP и голос вместе на втором SSH | 505–575 мс на втором SSH | 0,2–2,0% на втором SSH | — |

Все короткие пакеты вернулись в пределах окна наблюдения. При перегрузке крупным UDP общий сеанс дал 549 поздних ответов подряд в каждом повторе. При разделении максимум составил 7 и 182 пакета. Доля полученных крупных UDP-эхо выросла с 30–31% до 52–62%. Вариант, где крупный UDP делил второй SSH с голосом, дал 37–45% крупных ответов и оставил почти весь голос за порогом 200 мс.

При перегрузке крупным UDP пиковая очередь отправки мультиплексора сеанса с голосом уменьшилась с 31–39 КиБ до 0,5–2,0 КиБ. Общая очередь `netem` при этом доходила до 44–75 пакетов из 96 и 76–96 КиБ по снимкам каждые 250 мс. Часть этой очереди составляет заданная задержка распространения. При TCP в отдельных повторах доля своевременных ответов почти не менялась, а самая длинная серия поздних ответов при отправке даже выросла. Второй сеанс изолирует очередь приложения и повторные передачи своего TCP. Для предсказуемой задержки при заполненной физической линии нужна проверка управления объёмным трафиком.

В дополнительном прогоне снизили предложенную нагрузку крупного UDP до 3,36 Мбит/с. При тех же случайных потерях один SSH дал p95 1101 мс и 0 из 550 ответов до 200 мс. Два SSH дали 227 мс и 467 из 550. По одному повтору нельзя оценить эффект ограничения скорости. Этот прогон показывает, что задержки на общем TCP возможны и при предложенной нагрузке ниже номинала линии.

Контрольный прогон с теми же 5 Мбит/с и RTT 100 мс прошёл без заданного случайного сброса и джиттера. На скачивании отдельный SSH ухудшил p95 с 255 до 466 мс и долю ответов до 200 мс с 84% до 8%. Общая выходная очередь выросла с 40 до 96 пакетов и отбросила 11 IP-пакетов. Пик очереди отправки голосового мультиплексора составил 170 байт. При перегрузке крупным UDP p95 изменился с 283 до 314 мс, а своевременные ответы выросли с 1 до 79 из 550. Это контрольные одиночные замеры. Они показывают, что изоляция SSH сама по себе не гарантирует выигрыша при общей сетевой очереди.

На той же линии без случайных потерь снижение нагрузки с 5,76 до 3,36 Мбит/с подняло долю ответов до 200 мс с 14% до 87% в режиме двух SSH и уменьшило пик общей очереди с 87 до 37 пакетов. Один SSH с тем же ограничением дал 89% ответов до 200 мс. Максимальная серия поздних ответов при 3,36 Мбит/с составила 56 пакетов на одном сеансе и 5 на двух. Эти одиночные прогоны задают гипотезу для сравнения двух сеансов с управлением скоростью.

## Что менять в приложении

1. Экспериментальный режим с двумя независимыми SSH через один профиль, один конечный сервер и один VPN Android. Выделить второй сеанс для голосовых UDP-потоков. TCP, DNS и крупный UDP оставлять на общем сеансе. В цепочке RU → France открывать для каждого сеанса своё соединение до RU. Два канала внутри одной SSH-сессии делят один внешний TCP. [RFC 4254](https://www.rfc-editor.org/rfc/rfc4254.html#section-5)
2. На первом этапе выбрать голосовой профиль явно для тестируемого приложения. На Android привязка должна делаться при открытии UDP-потока по UID и адресу назначения, пока известны локальные адрес и порт. Для неизвестных потоков использовать общий сеанс. Размер отдельной датаграммы недостаточен, поскольку у QUIC тоже есть короткие пакеты. Закреплять выбранный путь до закрытия ассоциации, чтобы сохранить исходный UDP-сокет на выходном сервере. [Учёт UID](../android/app/src/main/java/dev/secrettunnel/android/AppTrafficAccounting.kt)
3. Ограничить общий бюджет памяти и число потоков обоих сеансов. Добавить измерение длинных серий поздних ответов и ожидания в очередях. При заполнении общей линии оценить управление скоростью крупных передач с учётом задержки. У второго SSH остаются собственные повторные передачи TCP, а оба сеанса продолжают делить очередь физической сети.
4. Проверить на Realme голос Discord через RU → France одновременно с загрузкой Instagram или передачей файла в Telegram. Замерить паузы, долю поздних пакетов, скорость передачи файла, CPU и память. Отдельно проверить простой, восстановление каждого сеанса и Wi‑Fi ↔ мобильная сеть.
