# Windows: передача управления установщику обновления

Исправление включено в версию 0.3.34. Разработка — в ветке
`codex/windows-update-handoff`.

Если прежний клиент закрывается, но не запускает установку, для первого перехода
на 0.3.34 скачайте `windows-x64-setup.exe` и запустите его вручную поверх
установленной версии. Пользовательские настройки и серверы сохранятся.

## Проблема

Приложение запускало PowerShell и закрывалось через 400 мс, проверив только
создание процесса. Не было подтверждения, что помощник прочитал параметры
и способен продолжить установку. Его stdout и stderr терялись. Установщик
запускался скрыто с `/S`, а ошибка после закрытия приложения не сохранялась
для следующего запуска интерфейса.

## Исправление

1. Создаётся отдельная копия установщика в `%APPDATA%\secret-tunnel\updates\install-*`.
   Её существование не зависит от времени жизни исходного скачанного файла.
2. Запускается системный Windows PowerShell с `CREATE_NO_WINDOW`, без поиска
   в PATH и без смешивания этого флага с `DETACHED_PROCESS`. Рабочая папка
   помощника находится вне каталога установленного приложения.
   Путь модулей помощника также закреплён за системным PowerShell 5.1:
   окружение PowerShell 7 не мешает загрузке `Get-FileHash` и `Start-Process`.
3. Помощник повторно сверяет SHA-256, удерживает дескриптор текущего процесса
   и подтверждает готовность. Приложение ждёт подтверждения до 30 секунд;
   при ошибке или таймауте оно остаётся открытым, помощник завершается.
4. После выхода приложения помощник освобождает его дескриптор и запускает
   NSIS с `/P /UPDATE /D=<исходный каталог установки>`: виден прогресс,
   сохраняется каталог установки и используются правила обновления Tauri.
5. Проверяется код завершения установщика. При успехе приложение открывается
   снова. При отказе помощник сохраняет ошибку и пытается открыть доступную
   установленную версию. Это повторный запуск, а не откат файлов NSIS.
6. Ошибка показывается при следующем запуске и в разделе «О программе».
   Серверы, SSH-ключи и настройки не сбрасываются.

## Диагностика

- `%APPDATA%\secret-tunnel\updates\last-error.txt` — последняя ошибка установки.
- `updates\last-helper.log` — вывод помощника, который не подтвердил готовность.
- `updates\install-*\update.log` — этапы конкретного обновления.
- `updates\install-*\helper-output.log` — stdout/stderr PowerShell.
- `updates\install-*\setup.exe` — сохранённый установщик при неудаче;
  после успешной установки удаляется, если Windows позволяет это сделать.

Политики Windows и антивируса не отключаются. Если они запрещают запуск
помощника или установщика, приложение сообщает об ошибке. Пользователь может
запустить проверенный установщик вручную.

## Регрессионные проверки

`windows_update` входит в обычные Rust-тесты desktop. Windows-тест использует
изолированные временные каталоги и небольшие исполняемые фикстуры, а не
переустанавливает пользовательскую копию приложения:

- до выхода старого процесса установщик не запускается;
- исходная загрузка может быть удалена после подтверждения готовности;
- установщик действительно заменяет тестовый EXE, затем приложение открывается;
- код отказа 42 сохраняется, установленная тестовая версия открывается снова;
- неверная контрольная сумма отклоняется до закрытия приложения;
- проверяются пробелы, кириллица и апострофы в путях, сохранность конфигурации;
- преждевременный выход помощника и отсутствие подтверждения не разрешают выход.
- некорректный `PSModulePath` вызывающего процесса не ломает установку.

Фикстура для Windows компилируется из `scripts/fixtures/windows-update-fixture.rs`.
В CI используется `rustc`. Для локального запуска в Windows без установленного
Rust можно заранее собрать её кросс-компилятором и указать путь в
`ST_WINDOWS_UPDATE_TEST_FIXTURE` при запуске тестового бинарника.

23 ноября 2026: в Windows 11 с Windows PowerShell 5.1 выполнены все пять
тестов модуля, включая установку, отказ, неверную контрольную сумму и
запуск с некорректным путём модулей вызывающей оболочки.
Проверка MSVC-цели отдельного модуля прошла. На macOS прошли 76 тестов desktop
(пять проверок live-соединений/изолированных сценариев пропущены),
TypeScript/Vite build и проверки общей версии. Реальный пользовательский
NSIS-установщик в этих прогонах не переустанавливался.
